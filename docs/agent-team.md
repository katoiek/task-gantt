# 開発チーム（サブエージェント）

短い依頼から、仕様 → 実装 → 検証のループを回すための3体構成。定義は `.claude/agents/` にある。

## 役割分担

| エージェント | 入力 | 出力 | やらないこと |
|---|---|---|---|
| **Planner** | 1〜4行の依頼 | `docs/specs/<slug>.md`（機能一覧・受け入れ条件・スプリント計画） | 実装詳細を決めない（DB 構成・ライブラリ・クラス名） |
| **Generator** | 仕様書＋担当スプリント | 実装コード＋`docs/specs/progress.md` の自己評価 | 担当スプリント外を作らない |
| **Evaluator** | 実装済みのアプリ | 採点結果と修正指示 | ソースコードを直さない |

## 回し方

```
依頼（1行）
  └→ Planner ──→ docs/specs/<slug>.md
       └→ Generator（スプリント1）──→ 自己評価
            └→ Evaluator ──→ 合格 ──→ Generator（スプリント2）へ
                          └→ 不合格 ─→ Generator（同スプリントを修正）
```

呼び出しは Task ツールで `subagent_type` に `planner` / `generator` / `evaluator` を指定する。

## 設計の意図

**Planner は「何を作るか」だけを書く。** 実装詳細を仕様に含めると、そこに誤りがあったとき全スプリントへ伝播する。Planner はその領域の正しさを検証できないため、判断を Generator に委ねる。

**Generator は1スプリントずつ進み、自己評価してから引き渡す。** 通らないものを通ったと報告させないことが、ループ全体の前提になる。

**Evaluator は読むのではなく操作する。** 「実装されているように見える」を合格の根拠にしない。5基準それぞれに閾値があり、1つでも下回れば不合格。総合点での埋め合わせはしない。

**Evaluator は直さない。** 評価者が直すと Generator の自己評価が働かなくなり、同じ欠陥が繰り返される。

## Playwright MCP

Evaluator はブラウザ操作に Playwright MCP を使う。`.mcp.json` に定義済みだが、**セッション開始時に承認が必要**。

このリポジトリ（Obsidian プラグイン）自体の検証には使えない。Obsidian は Electron デスクトップアプリで、Playwright MCP が繋がるのはブラウザだけ。この構成は Web アプリを対象とした汎用チームとして用意している。ブラウザで操作できない対象に対しては、Evaluator は CLI・API・テストスイートなど利用可能な手段へ切り替え、検証できなかった項目を「未検証」として扱う（未検証は合格の根拠にならない）。
